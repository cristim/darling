# mldr regressions

Host-compiled regression programs for the loader. Each one is a standalone `main`
that prints what it checked and exits non-zero on the first disagreement, so it can
be run without the guest, without darlingserver and without a build tree.

## Why here and not in `tests/`

The repository's `.gitignore` excludes `tests`, and the only content tracked under it
is `tests/src/bin/*/*.bin`, build output. A new test *source* there would need a
force-add against the repository's own rule, so these live beside the code they
cover instead. Nothing in `src/startup/mldr` is built by adding to this directory:
the CMake target lists its sources explicitly, so a stray `.c` here is not compiled
into mldr.

## Running one

`rtsig.h` is generated by the build (`src/startup/CMakeLists.txt`, the `rtsig_h`
target) and defines `LINUX_SIGRTMIN`/`LINUX_SIGRTMAX`, which the tests need. Point
the compiler at wherever the build put it, then compile and run from the repository
root so the default source path resolves:

    clang -std=gnu11 -D_GNU_SOURCE -pthread \
        -I src/startup/mldr/include -I <build dir>/src/startup \
        -o thread_startup_sigmask \
        src/startup/mldr/regressions/thread_startup_sigmask.c
    ./thread_startup_sigmask

If the build tree is not available, rtsig.h is two defines; the values used by
darlingserver are `LINUX_SIGRTMIN 43` and `LINUX_SIGRTMAX 64`.

## thread_startup_sigmask

Covers the signal mask a new thread runs with while it starts up: that the startup
set blocks ordinary signals, that it leaves `LINUX_SIGRTMIN` and `LINUX_SIGRTMIN + 1`
alone, that the set reaches a thread before its first instruction, and that the mask
restored afterwards is the *creating* thread's.

The last one is why the test also reads `elfcalls/threads.c`. On a platform with
`pthread_attr_setsigmask_np` the kernel applies the startup set during `clone`, so by
the time `darling_thread_entry` runs its own `SIG_BLOCK`, the save it takes is the
startup set rather than the creating thread's mask. Restoring that save compiles,
runs, and leaves every new thread blocked for the rest of its life, realtime signals
included, which darlingserver needs in order to hold and release it. No behavioural
check can catch it, because the wrong value is perfectly valid; the test therefore
checks which mask the loader restores.

Pass a path to check a different copy of the source:

    ./thread_startup_sigmask /path/to/elfcalls/threads.c

### A correction to the history of this area

`aadf1394d`'s message says the realtime signals are left unblocked "so a thread
suspended while it starts can then still be resumed". That is the right behaviour
but the wrong reason to have stated, and it is worth recording here because the
commit stays as written.

The exclusion is not primarily about resuming a suspended thread. It is that
darlingserver's own RPC code, `dserver_rpc_hooks_atomic_begin` in
`src/startup/mldr/resources/dserver-rpc-defs.h`, builds its mask the same way:
`sigfillset`, then `sigdelset` for `LINUX_SIGRTMIN` and `LINUX_SIGRTMIN + 1`. That is
the repository's established convention for any mask held across an RPC, and the
loader now matches it. The reason the convention exists is that these two signals
carry darlingserver's thread hold and suspension mechanism
(`dtape_hooks->thread_send_signal(thread->context, LINUX_SIGRTMIN)` in `thread_hold`,
in `src/external/darlingserver/duct-tape/src/thread.c`), so blocking them during a
window that can span an RPC would break that mechanism rather than protect anything.
The test asserts the exclusion, and asserts it as a property of the mask; it does not
depend on which of these readings is correct, since both require the same two signals
to be left out.
